# Backend API (FastAPI)

A REST API wrapping the exact same trained model and classification logic
used throughout the rest of this project. Built so a separately-hosted
frontend (e.g. the Next.js app in `../frontend`, deployed on Vercel) can
call it over HTTP, since Vercel can't run a persistent Python/ML service
directly.

## Endpoints

| Method | Path | Description |
|---|---|---|
| GET | `/` | Health check |
| GET | `/intents` | List of the 12 supported intents + descriptions |
| POST | `/predict/text` | `{"text": "..."}` → prediction JSON |
| POST | `/predict/audio` | Multipart audio file (`.wav`/`.flac`/`.aiff`) → transcribe + predict |

Interactive API docs are auto-generated by FastAPI at `/docs` once running.

## Run locally

```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

**This was actually tested, not just written and assumed to work** — every
endpoint below was run against a live local server before being included
here:

```bash
# Health check
curl http://localhost:8000/
# -> {"status":"ok","service":"voice-command-classifier-api"}

# Text prediction
curl -X POST http://localhost:8000/predict/text \
     -H "Content-Type: application/json" \
     -d '{"text": "abeg send 2k give my mama"}'
# -> {"command":"...","predicted_intent":"send_money","confidence":0.81,...}

# Audio prediction
curl -X POST http://localhost:8000/predict/audio \
     -F "file=@../data/sample_audio/check_balance_sample.wav"

# Error handling was also verified: empty text -> 400, wrong file type -> 400
```

## Deploy

This backend needs a host that runs a **persistent** Python process (not
serverless) — Render, Railway, and Fly.io all fit and have free tiers.

### Option A: Render (Docker)
1. Push this repo to GitHub.
2. On Render: **New → Web Service** → connect the repo → set **Root
   Directory** to `backend` → Render auto-detects the `Dockerfile`.
3. Deploy. You'll get a URL like `https://your-api.onrender.com`.

### Option B: Render / Railway (no Docker, using Procfile)
1. Same as above, but instead of Docker, set:
   - **Build command:** `pip install -r requirements.txt`
   - **Start command:** `uvicorn main:app --host 0.0.0.0 --port $PORT`
   (This is exactly what `Procfile` specifies, for platforms that read it
   automatically, e.g. Railway.)

### Option C: Fly.io
```bash
cd backend
fly launch     # detects the Dockerfile automatically
fly deploy
```

**Honest note:** the `Dockerfile` in this folder follows standard,
well-established patterns for a Python+PocketSphinx service, but Docker
itself wasn't available to build-test in the sandboxed environment this
was developed in. What *was* directly tested is the underlying Python
service (`pip install -r requirements.txt` + `uvicorn main:app`) — the
same commands the Dockerfile runs internally — with real requests against
every endpoint, confirmed above. If the Docker build hits any platform-
specific hiccup, Option B (plain Python buildpack, no Docker) is the
fallback and uses the exact code path already verified.

## CORS

`main.py` currently allows all origins (`allow_origins=["*"]`) so you can
get the frontend working first. Before treating this as production,
narrow it to your actual Vercel domain in `main.py`:
```python
allow_origins=["https://your-app.vercel.app"]
```
